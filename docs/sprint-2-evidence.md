### Локальный замер производительности

Apple M4, 32 ГБ, шаблон «Вклад для пенсионеров», три варианта и seed 42. Замерено время одного вызова `run_experiment` без UI, сети банка и записи в архив. В демо медианы по пяти прогонам составили 4,1, 17,7 и 65,2 мс для 50, 200 и 1 000 профилей соответственно. Во всех запусках получены все запрошенные оценки. Эти цифры относятся к эвристическому демо.

Модельный прогон выполнен в LM Studio с `qwen/qwen3-vl-4b` в вероятностном режиме. Кэш приложения отключён, перед замером выполнен один запуск на одном профиле. Каждый замер включает 18 ответов для шести профилей и отдельный запрос простого подхода. Фоновая активность машины и кэш префиксов сервера не контролировались.

| Параллельность | Время запуска | Валидные ответы | Простой подход |
| ---: | ---: | ---: | --- |
| 1 | 124,8 с | 18 из 18 | получен |
| 4 | 120,9 с | 18 из 18 | получен |

Для воспроизведения настройте локальный сервер модели и выполните эти команды. Время CLI включает небольшие затраты запуска и печати.

```bash
export LLM_BASE_URL=http://127.0.0.1:1234/v1 LLM_MODEL=qwen/qwen3-vl-4b LLM_JSON_MODE=text
export LLM_EXTRA_BODY='{"chat_template_kwargs":{"enable_thinking":false}}'
export DVOINIK_ELICITATION=probability DVOINIK_LLM_CACHE=0
python cli.py senior_deposit --n 1 --seed 42 --concurrency 1
for concurrency in 1 4; do
  /usr/bin/time python cli.py senior_deposit --n 6 --seed 42 --concurrency "$concurrency"
done
```

Оценка перед запуском теперь учитывает пробный запрос, очередь вариантов и отдельный запрос простого подхода. Для шести профилей, трёх вариантов и параллельности 4 это восемь последовательных групп запросов вместо прежних пяти. При значении 3 с на запрос расчёт даёт 24 с, поэтому для планирования в выбранной среде задержку надо измерить отдельно. Разница в 3,9 с между двумя одиночными запусками не позволяет оценить устойчивый выигрыш от параллельности. Замер не покрывает параллельные исследования нескольких команд, банковский контур или эксплуатационные гарантии.

Параллельность внутри запуска — 2. Время отсчитывалось с начала работы движка. Провайдер передал расход для каждого вызова. Повтор заново запросил только оценку простым промптом. Для последних двух строк кэш приложения отключили и через барьер одновременно запустили два вызова `run_experiment` в разных потоках. Оба завершились за 90,77 с суммарного времени по часам. Каждый снимок сохранил собственный расход. Проверка охватывает движок на одном локальном сервере. Для бюджета пилота ещё нужны целевой размер аудитории, тариф или стоимость машино-часа, а для эксплуатационного норматива — повторные замеры через очередь заданий.

Для повторения первых двух строк используйте параметры модели из предыдущего примера и новый каталог кэша. Для сопоставления самых разных снимков подойдёт та же команда журнала.

```bash
run_dir=$(mktemp -d)
export DVOINIK_LLM_CACHE=1 DVOINIK_LLM_CACHE_PATH="$run_dir/cache.sqlite3"
for run in cold warm; do
  python cli.py senior_deposit --n 2 --seed 42 --concurrency 2 --output "$run_dir/$run.json"
done
python -m dvoinik.run_journal "$run_dir/cold.json" "$run_dir/warm.json"
```

## Демонстрация на 7–10 минут

1. Назвать задачу: подготовить исследование двух предложений для выбранного сегмента. Открыть архив и создать исследование.
2. Изменить вопрос/текст, перейти к аудитории, обновить страницу и показать восстановление черновика.
3. Показать режим, число оценок и оценку нагрузки; выполнить демо-запуск без внешней модели. Демо обозначить до показа результатов.
4. В отчёте показать ограничения и следующий шаг. Продемонстрировать сегменты и причины, затем комплект живого опроса.
5. Показать тестовый CSV как техническую фикстуру. Предпросмотр не сохранять как реальную полевую проверку. Показать отмену ухода и явную отмену предпросмотра.
6. Скачать резюме и показать результаты локальной технической проверки защиты. Показать, куда отправляются запросы при выбранной конфигурации модели.
7. Открыть экономику: изменить цену/число клиентов/нагрузку, объяснить разницу операционной безубыточности и возврата начальных затрат.
8. Закончить конкретными открытыми гипотезами и предложением пилота, а не утверждением о доказанном спросе.

## Интервью для проверки ценности

Цель — 5–7 бесед с продактами/исследователями и отдельная беседа с владельцем бюджета. Количество — план качественного исследования; проведённые беседы здесь не заявляются.

- Расскажите о последнем исследовании банковского предложения: вопрос, сроки, люди, фактические затраты и что стало результатом.
- Как выбирали, какие варианты перенести в живое исследование? Что пришлось переделать и почему?
- Кто согласовывал доступ к данным и использование модели? Где проходила граница допустимой передачи?
- На каком этапе продукт мог бы сэкономить время? Что всё равно осталось бы делать вручную?
- Какие доказательства нужны, чтобы вы доверили инструменту подготовку следующего исследования?
- Кто покупает такие решения, из какого бюджета и какие этапы закупки обязательны?

Для каждой беседы: дата, роль без персональных данных, разрешённые заметки, наблюдаемый пример, гипотеза до/после, следующий шаг. Не заменять фактические затраты ответом «сколько готовы платить».

## Критерии готовности к пилоту

- Есть согласованный вопрос, одна целевая аудитория и неизменяемые версии предложений.
- Указаны конечные точки модели и эмбеддингов, разрешённые данные и ответственные за доступ/удаление.
- Техническая демонстрация и security demo проходят в целевом окружении.
- Согласованы объём/дата окончания живой проверки, практически интересная разница, обработка пропусков и метод анализа.
- До старта зафиксированы прогнозы моделей, baseline, параметры и экспорт.
- Отдельно измеряются время подготовки, затраты, качество материалов и совпадение с ответами людей.
- Стоп-условия: нарушение границы данных, отсутствие разрешения на набор, критический дефект доступа, массовые невалидные ответы модели. Пилот приостанавливается до устранения причины.

Запуск после этих технических изменений сам по себе не подтверждает выполнение организационных условий пилота.

## Происхождение ответов

Добавлен необязательный протокол сбора: способ набора, начало/конец периода,
распределение вариантов и примечание. Сервер проверяет структуру, длину, UTF-8,
даты и порядок периода. Протокол сохраняется и экспортируется с проверкой;
HTML экранирует пользовательский текст, конфликт сохранения не перезаписывает чужую версию.
Старые снимки явно обозначают неизвестное происхождение.

Браузерная проверка выполнена с технической фикстурой: поля дошли до предпросмотра,
отмена сохранила сведения для редактирования; тестовый опрос в архив не записан.
Независимый обзор нашёл и помог устранить несогласованность распределения в UI/экспорте
и удаление сведений при отмене предпросмотра.

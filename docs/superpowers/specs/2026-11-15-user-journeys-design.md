# Двойник: пользовательские сценарии и UX

Статус: предложение для продуктового обсуждения, не описание уже реализованных функций.
Дата: 15 ноября 2026. Основание: текущий код и проверки интерфейса; интервью с пользователями не проводились. Приоритеты ниже — рабочие гипотезы.

## Назначение

Помочь продуктовой команде банка подготовить проверку предложения: сформулировать вопрос, исследовать возможные реакции и барьеры, подготовить живое исследование и сопоставить его ответы с симуляцией. Результат работы — обоснованный следующий шаг с видимыми ограничениями. Синтетические доли не выдаются за прогноз спроса.

Основной пользователь — продуктовый менеджер. Исследователь уточняет методику и состав аудитории. Руководитель читает резюме и принимает решение о дальнейшей проверке. Администратор управляет доступом. Это пользовательские роли, а не предложение немедленно добавить четыре типа аккаунтов. Респондент проходит внешнюю анкету и не должен видеть симуляцию.

## Подходы

1. Каталог инструментов: оставить отдельные вкладки и дать пользователю самому собирать процесс. Удобен опытному исследователю, требует знания методики.
2. Путь исследования с доступными экспертными настройками — рекомендуемый подход. Следующий шаг зависит от состояния исследования, при этом пользователь может вернуться к любой доступной части.
3. Чат как основной интерфейс: удобен для формулировки вопроса, но затрудняет сверку вариантов, аудитории и воспроизводимость. Возможное дополнение позже.

Выбор второго подхода — предложение исполнителя, а не результат пользовательского исследования.

## Карта пути

Вход / знакомство → выбор задачи → черновик → предложения → аудитория → проверка настроек → запуск → разбор результата → подготовка живой проверки → предпросмотр ответов → сохранение проверки → решение / следующая итерация.

Ветви: открыть пример; импортировать снимок; вернуться к черновику; открыть завершённый отчёт; восстановиться после ошибки; сравнить итерации; экспортировать резюме. Эти ветви не должны заставлять повторять основной путь.

## Что уже есть

- Двухшаговый Composer: предложения и аудитория, шаблоны, настройки запуска, оценка нагрузки.
- Черновики по сценариям в памяти Workspace (`frontend/src/app/useDrafts.ts`). Перезагрузку не переживают.
- Фоновый запуск, обнаружение активного задания, отмена, обработка ошибок (`useJob.ts`, `JobView.tsx`).
- Архив с поиском, фильтрами, сравнением, импортом и переходом к опросу (`Library.tsx`).
- Вкладки отчёта в URL, ограничения качества, причины отказа, гипотезы, происхождение итераций.
- Комплект опроса, CSV-предпросмотр отдельно от сохранения, проверка конфликтов при сохранении (`ValidationPanel.tsx`).
- Изолированные архивы владельцев; экспорт файлов. Общего доступа по ссылке на отчёт нет (`docs/access-proposal.md`).
- Мобильная компоновка. Проверены браузерные размеры; реальные устройства, клавиатура и экранные дикторы ещё не проверены.

## Модель состояния

Не использовать один универсальный статус «готово».

1. Работа: черновик → запуск → завершено / отменено / ошибка; отдельный признак несохранённого результата.
2. Источник: демонстрация / LLM; импорт — происхождение, а не вид модели.
3. Проверка: ответов людей нет / предпросмотр / сохранённая проверка. «Сохранена» не равно «подтверждена».
4. Качество: валидные ответы, ошибки, коррекции, покрытие сегментов. Это отдельные признаки, а не рейтинг достоверности с выдуманным порогом.
5. Решение: добровольная заметка пользователя; не вычисляется автоматически из максимального процента.

Основное действие определяется состоянием: продолжить черновик → открыть запуск → восстановить запись → разобрать ошибки → подготовить опрос → сохранить предпросмотр → изучить расхождения → создать следующую итерацию. При нескольких проблемах сначала защищаем данные и показываем блокирующую причину.

## Предлагаемая структура экранов

Архив: «Продолжить работу» (черновик/запуск), затем поиск и завершённые исследования. Не дублировать запуск как готовый отчёт.

Создание: «Вопрос и предложения» → «Аудитория» → компактная проверка настроек перед запуском. Не добавлять обязательный длинный onboarding. Название может предлагаться из вопроса, но остаётся редактируемым.

Отчёт: что сравнивали → что наблюдали в симуляции → ограничения → следующий шаг. Числа, причины и голоса доступны глубже. Удалённая/недоступная исходная запись не ломает дочернее исследование.

Опрос: подготовка материалов → файл → покрытие/ошибки → предпросмотр → явное сохранение/замена → расхождения. Внешний опрос и рекрутинг не изображаются как встроенные возможности.

## Очерёдность внедрения

### Итерация 1: не терять работу
US03–05, US20–21, US29. Сохранение черновика и этапа, понятный статус сохранения, восстановление, явная замена проверки с доступной выгрузкой прежнего снимка, защита custom-черновика от перезаписи, предупреждение о несохранённом предпросмотре, ошибки рядом с полями.

Начальный объём: один черновик на шаблон в текущей вкладке; восстановление после reload. sessionStorage с ключом владельца и очисткой на выходе соответствует текущему правилу «выход очищает черновики». Это не сохранение между устройствами или после закрытия вкладки. Ошибка/недоступность хранилища видна, редактирование остаётся доступным. Постоянные серверные черновики — отдельная следующая история с миграцией и проверками доступа. Не помещать CSV ответов людей в browser storage.

### Итерация 2: понятный результат
US08, US13–15, US22–24. Проверка настроек, блок следующего шага, покрытие опроса и статусы архива. Общие правила статусов должны применяться в карточке, отчёте и экспорте.

### Итерация 3: цикл исследования
US16–18, US28, US30–32. Сопоставимость итераций, план проверки и заметка решения. Совместные проекты и доступ по ссылке требуют отдельного обсуждения прав.

## Проверка UX

Провести 5–7 модерируемых сессий с представителями целевой роли. Это качественная проверка сценариев, не статистическое подтверждение эффективности продукта. Задания: создать исследование; прервать и восстановить ввод; объяснить результат без живых данных; исправить CSV; заменить проверку; передать резюме коллеге. Записывать завершение без подсказки, места ошибок, потерю ввода, понимание различий демо/модель/опрос и первого следующего действия. Не задавать целевые проценты до исходного замера.

Технический набор: регрессионные тесты состояний, изоляции черновиков и конфликтов сохранения; браузерные проходы; ширины 320/390/768/desktop; реальный iOS Safari и Android Chrome с клавиатурой, поворотом экрана, загрузкой файла, VoiceOver/TalkBack. Автотесты не заменяют эти проверки.

## Открытые решения

- Для первого пилота предполагается индивидуальный архив менеджера, обмен через экспорт. Совместный проект не считается уже разрешённой возможностью.
- Черновик первого этапа переживает обновление текущей вкладки; срок и место постоянного хранения банковских предложений требуют отдельного продуктового решения.
- Практически значимый эффект и дизайн живого исследования задаёт исследователь; приложение показывает предпосылки и не выбирает их скрыто.
- Полная «поддержка всех кейсов» недостижима одним списком: карта обновляется по результатам пилота и реальным обращениям.

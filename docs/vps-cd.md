# Автоматическая выкладка на VPS

Push в `main` запускает тесты Python, проверки фронтенда и сборку контейнера.
После успеха задача `promote-vps` без force-push обновляет ветку `deploy/vps`.
Запуски pull request ничего не разворачивают. VPS через systemd проверяет этот
публичный ref примерно раз в минуту. SSH-пароль, ключ доступа к VPS и
ключ модели не нужны GitHub Actions.

Каждая сетевая операция Git ограничена 35 секундами. При ошибке скрипт повторяет
её один раз. Если повтор тоже завершается ошибкой, работающий контейнер остаётся
доступен, а таймер запускает следующую попытку. Уже собранный образ можно
использовать повторно, если его метка совпадает с допущенным коммитом.

Скрипт собирает зафиксированный коммит, проверяет контейнер на отдельном
loopback-порту 8502 с временным хранилищем и снова сверяет актуальность коммита.
Перед заменой снимает согласованную копию SQLite в
`/var/lib/dvoinik-cd/backups/`. Новый контейнер сохраняет прежний том
`dvoinik-misisx-data` и использует `/etc/dvoinik/runtime.active.env`, в котором
администратор VPS выбирает текущие настройки приложения и модели. Прокси и
SSH-туннель до LM Studio не перезапускаются.

Если новая версия не отвечает по HTTPS или архив доступен без входа, скрипт
возвращает предыдущий контейнер. Копия SQLite остаётся для ручного восстановления
при необходимости. Копии на том же VPS защищают от ошибки обновления; для пилота
нужно отдельно настроить резервирование вне сервера. Задания в оперативной очереди
и выполняющиеся исследования удерживают общую блокировку в томе
`dvoinik-misisx-data`. При активных заданиях скрипт откладывает обновление до
следующей проверки. Получив эксклюзивную блокировку, скрипт держит её до конца
выкладки или отката. Запрос на запуск в этот интервал получает HTTP 409 с
сообщением о необходимости повторить попытку. При аварийной остановке расчёт
прерывается. После перезапуска владелец может открыть настройки из списка
«Прерванные исследования» и заново запустить расчёт. На время защиты таймер
можно остановить и затем снова включить.

Установка на уже работающем VPS выполняется один раз от root. Сначала проверьте,
что `runtime.active.env` указывает на файл реально используемых настроек (для
репетиции на M4 — `runtime.m4.env`). Не размещайте эти файлы в GitHub.
При переходе со старого скрипта сначала выкладывают контейнер с
`DVOINIK_DEPLOY_LOCK=/data/.deploy-jobs.lock` в период без исследований, затем
устанавливают новый скрипт. Он проверяет поддержку блокировки у обоих контейнеров.

```bash
install -m 755 deploy/vps-update.sh /usr/local/sbin/dvoinik-vps-update
install -m 644 deploy/dvoinik-cd.{service,timer} /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now dvoinik-cd.timer
```

На GitHub ветка `deploy/vps` указывает на версию, допущенную к выкладке. Фактически
развёрнутый коммит и состояние таймера проверяйте на VPS:

```bash
docker inspect -f '{{index .Config.Labels "org.opencontainers.image.revision"}}' dvoinik
systemctl list-timers dvoinik-cd.timer
journalctl -u dvoinik-cd.service -n 40 --no-pager
```
